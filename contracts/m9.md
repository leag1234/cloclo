# M9 — projets, conversations et mémoire de faits

Source: docs/15 M9 ; REQ-ENG-002/004/005/007/009, REQ-FIN-002, POC-P6.
Contrat séparé avant implémentation, sans modification des vérificateurs protégés.

## Stockage et portée

Retrieval possède un nouveau stockage local sous BRAIN/projects.sqlite (0700 pour
le répertoire, 0600 pour le fichier). Il regroupe projets, conversations, documents,
instructions et faits. Aucun accès direct de l'orchestrateur à ce stockage.
Les données restent locales, ignorées par Git, sans export dans les rapports.
Le corpus M2 reste indépendant ; une requête avec projet ne consulte que ce projet.
Aucune migration ni suppression de données M2/M7 existantes.

Les identifiants projet/conversation/document/fait sont des UUID créés par serveur.
Chaque accès enfant vérifie le parent dans la requête SQL. Les citations de projet
ne sont jamais résolues par la route globale M7. Les IDs inconnus ou appartenant à
un autre projet produisent 404, sans contenu ni détail fournisseur.
Le PoC est mono-utilisateur sur loopback ; un ID de projet est une portée logique,
pas une autorisation multi-utilisateur. Aucun accès public supplémentaire.

## API retrieval, préfixe /projects

- POST /projects {name, instructions?} : crée un projet ; GET /projects : liste.
- GET /projects/{p} : projet ; PATCH même chemin {name, instructions} : remplace.
- POST /projects/{p}/conversations {name} : crée une conversation.
- GET /projects/{p}/conversations : liste ; GET /projects/{p}/conversations/{c} :
  échanges persistés. Une conversation ne change pas de projet.
- POST /projects/{p}/documents {name, text, lang} : document textuel découpé avec
  le pipeline existant et indexé via embeddings gateway ; GET même chemin : liste.
  Les formats documentaires existants restent gérés par leur extracteur M2.
- POST /projects/{p}/search {query} : classement hybride M2 exclusivement sur les
  chunks du projet ; GET /projects/{p}/sources/{chunk_id} : résolution scoped.
- GET /projects/{p}/facts : faits inspectables (id, text, conversation_id).
- PATCH /projects/{p}/facts/{f} {text} : correction utilisateur prioritaire.
- DELETE /projects/{p}/facts/{f} : effacement individuel ; DELETE /projects/{p}/facts :
  effacement total. Les conversations archivées ne servent jamais à réextraire les
  faits effacés. Un compteur de révision invalide les consolidations en cours lors
  d'une correction ou d'un effacement (pas de résurrection à la fin d'une requête).
- POST /projects/{p}/context {conversation_id, query} : instructions, faits
  pertinents identifiés comme mémoire, révision et historique de cette conversation.
- POST /projects/{p}/turns {conversation_id, question, answer, facts, revision} :
  enregistrement atomique de l'échange ; nouveaux faits seulement si la révision
  est encore courante. Faits extraits uniquement du nouveau message utilisateur.

Entrées validées : nom 1..120 caractères, instructions <=4000, document <=32000,
question/réponse <=32000, fait 1..500, <=8 faits proposés par tour. Identifiants
validés ; SQL paramétré. Corps HTTP borné. Erreurs typées sans texte confidentiel.

## Adaptateur et interface

POST /v1/chat/completions accepte project_id et conversation_id ensemble ou aucun.
En mode projet, le serveur charge l'historique associé ; le client ne peut injecter
l'historique d'un autre projet. Le dernier message utilisateur reste la question.
Les faits pertinents sont séparés des instructions et des sources documentaires.
Le résultat distingue explicitement mémoire et citations documentaires.
La consolidation automatique utilise le gateway existant : aucun SDK fournisseur,
nom de modèle, prompt en dur hors répertoires autorisés. Les faits ne sont pas un
résumé brut ni une copie de l'historique. Les corrections/effacements ne sont pas
annulés par une extraction tardive. Les anciens échanges restent inspectables,
mais ne réintroduisent pas un fait supprimé dans le contexte futur.

Interface basique locale sur l'adaptateur : sélection/création du projet et de la
conversation, instructions/notes documentaires, faits visibles, modifiables et
effaçables, chat utilisant ces IDs. HTML échappé, rendu par textContent, pas de
scripts tirés de contenus utilisateur. Open WebUI M7 reste disponible.

## Budgets, preuves et ordre d'implémentation

Budget global par requête incluant consolidation <=0,05 EUR, <=120 s ; réservation
avant chaque appel. Pas de GPU créé, coût infra ajouté 0 EUR/h. Réseau fournisseur
uniquement via gateway ; mémoire privée non envoyée au moteur de recherche web.
Tests n'utilisent que des entrées synthétiques et cassettes dédiées aux tests.
Rapport BRAIN/eval/memory.json contient des booléens calculés depuis assertions
réelles : fact_reused_across_conversations, projects_isolated, erasure_effective,
memory_vs_source_distinguished ; aucun contenu utilisateur.

Tests: persistance après réouverture ; conversation du mauvais projet ; recherche
et citation d'un autre projet ; fait effacé/corrigé pendant requête ; extraction
malformée, timeout, budget et retour fournisseur ; injection HTML ; mémoire/source ;
requêtes sans projet M7 inchangées. make test-memory puis make verify-m9 exécutent
ces contrôles. La CI existante appelle le gate via scripts/test.sh, sans modification
du workflow. La CI du contrat seul ne prouve pas l'achèvement de M9.
